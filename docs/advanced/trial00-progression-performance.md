# Trial00 连续推进性能定位

日期：2026-09-14。基于已完成的 View 消费需求调度，Apple M4 / Godot 4.7.2 Mono / Metal Forward+ / 2560×1440 / 默认 VSync / 显示器报告 120Hz。

## 结论与下一项修复

下一项优先修复应落在 **角色 appearance 转场准备**，而不是继续调整帧率设置。

复测的 19 次实际 appearance 转场中，4 次源、目标图层集合完全相同，却仍创建两份完整角色副本、申请双离屏输入并准备转场。仅这 4 次的同步准备调用分别耗时 5.880、7.832、11.234、6.867ms；它们还有后续渲染与资源回收工作。120 FPS 的整帧预算只有 8.333ms。

真正换装也有过量复制：梅露露每份副本复制 121 层，实际选择 11–12 层；艾玛复制 126 层，实际选择 9–10 层。应先省去稳定、等价 appearance 的视觉准备，再优化副本构建范围。这些数据确认了具体的同步开销；**不能将所有长帧都归因于它，更不能把异步准备总耗时当作 CPU 阻塞时间。**

定位轮只增加可选诊断入口和计时标记。随后已实现 appearance 修复，具体落地与修复后数据见文末。

## 具体证据

### 1. 稳定状态下的重复 appearance 仍执行视觉转场准备

复测在 `LayeredCharacterActor.PrepareAppearanceTransitionAsync()` 解析源和目标后比较实际图层集合，得到以下四次相等结果：

| 指令 | 同步准备 ms |
|---|---:|
| `Alisa appearance:Angry1,Option-ArmL-Off` 的重复设置 | 5.880 |
| `Meruru appearance:Normal1,ArmR8_1,ArmL8,Eyes1_Normal_Open2,Mouth1_Normal_Open2` 的重复设置 | 7.832 |
| `Meruru appearance:Normal1,ArmR1_1,Eyes1_Normal_Open3,Mouth1_Smile_Closed1` 的重复设置 | 11.234 |
| `Meruru appearance:Normal1,ArmR5_1,ArmL2,Eyes1_Pensive_Open2,Mouth1_Normal_Open1` 的重复设置 | 6.867 |

这是图层集合等价，不只是未经解析的字符串相等。四次约占实际 appearance 转场的 21%，合计约 31.8ms 的同步准备调用耗时；这些调用分散在多个对白边界，不能从平均帧耗时直接减去这个总量。

后端 `GodotDirectionActorTreeBackend.PrepareAsync()` 目前只检查原角色可见、转场非 cut、时长大于零，随后总是创建 appearance visual。提交路径也假定 `visuals[id]` 存在。修复要同时调整准备结果和提交行为，不能只加一个 early return。

### 2. 复制完整角色层级占据显著的同步准备预算

`LayeredCharacterActor.CreateComposite()` 先 `layerComposite.Duplicate()`，随后遍历全部 Sprite 设置可见性并应用 masking。源和目标各执行一次。

| 数据 | 首轮 | 复测 |
|---|---:|---:|
| 完整副本次数，含启动预热 | 82 | 82 |
| 单份副本中位耗时 ms | 2.011 | 1.673 |
| 单份副本 P95 ms | 3.154 | 3.962 |
| 单份副本最大耗时 ms | 10.192 | 8.625 |
| 捕获池 acquire 中位 ms | 0.224 | 0.342 |
| 捕获池 release 中位 ms | 0.455 | 0.573 |

复测实际 appearance 的同步准备中位耗时 6.867ms，包含两份副本和首次进入异步等待之前的同步工作。这是计时范围的墙钟耗时，仍可能包含系统调度或 GC 的影响，不是线程 CPU 自耗时。

只复制当前 `Visible` 节点也不够：需要保留选中层的遮罩依赖、排序、原点、材质与 group opacity，以及实时转场源的行为。第一版宜局限于已知的 layered actor 实现。

### 3. GC 与资源加载不是全部推进长帧的解释

- 推进阶段 42 / 51 个 >16.67ms 间隔中，仅 3 / 7 个伴随 GC 计数增加。GC 可能解释其中一部分，无法解释多数长帧；本轮不是 GC 暂停事件级追踪。
- 角色图集的加载都出现在启动阶段，推进时主要出现语音资源的异步预读。
- 53 次资源同步取回调用的最大值为 1.350 / 0.554ms，中位值为 0.029 / 0.025ms。没有测到它作为几十毫秒同步阻塞的证据。
- `resource.load.async`、`direction.prepare` 以及 `command` 的时长包含等待，不能据其总时长认定卡住主线程。嵌套 span 的时长也不能相加当作 CPU 时间。
- 这不排除后台纹理上传、首次绘制、驱动同步或未埋点路径的工作。

### 4. 启动预热另有独立成本

11 名角色各执行两次 `WarmAppearanceRenderingAsync()` 内的 snapshot 准备，总计 22 对捕获、44 次完整层级复制。snapshot 路径会冻结源、目标两张视口图像，即此路径按代码产生 44 次图像读回。

这些预热旨在避免首次换装分配和 shader 使用尖峰，不应直接删除。后续可评估预热是否只需渲染完成而无需 CPU 冻结读回，以及是否可按捕获池容量和 shader 使用情况安排预热。本轮尚未对这些读回分别计时，也没有进行关闭预热的对照，因此未将启动 113–130ms 尖峰归因于某次具体读回。

## 推荐修复顺序与坑

1. **避免稳定、等价 appearance 的视觉准备。**依据已解析外观身份判断，保持持久状态、旧转场结算、显式时长和 `wait` 的契约。准备/提交必须共同认识“没有新 visual”的结果；活动中的转场不能只凭目标字符串相同直接跳过。验证别名等价、连续相同指令、未结束转场、取消、回滚、保存恢复及副作用。
2. **缩小 layered 转场副本。**从已解析图层集合及遮罩依赖构造源、目标，不为 12 个选中层复制 121 个节点。先保留现有输入生命周期和捕获池，验证遮罩、排序、alpha、group opacity 与重叠转场；不混入通用角色渲染图重构。
3. **独立调整启动预热。**确认可用无冻结读回的渲染准备替代目前 snapshot 预热，再测首次显示/换装是否退化。保留稳态与启动两套指标。

验收继续使用同一 24 句轨迹：关注 appearance 准备时长、实际副本/捕获次数、P95/P99 和长帧数量，并用像素回归保证语义。不能用“去掉所有 dissolve”作为正式修复，也不能仅看平均 117→120 来判断成功。

## 测量限制与验证

复测为所有新增视口启用了 Godot 原生渲染计时，但 GPU 查询始终返回 0，属于本轮不可用的指标，不表示 GPU 耗时为零。`RenderTextureMemUsed` 出现明显不合理的无符号回绕值，复测将其记为 `NaN`，汇总丢弃该指标。其他 Godot Performance monitor 可能延迟更新，不能精准归因到某个同帧事件。后续若需要确认 GPU/上传占比，应使用可工作的 Metal/系统时间线。

两轮采样设置略有不同：复测增加等价图层标记和原生视口计时，因此它们是定位复现，不是严谨的优化前后 A/B。采集本身也有开销；本轮不存在性能修复收益的宣称。

构建零警告/错误，`tools/test.sh --fast` 的 582 项 C# 单元测试、Godot headless 集成及失败退出码检查通过，日志见复测目录 `tests.log`。真实运行完整走到末尾菜单。启动仍有原先的 TextLineProvider YarnProject 配置报错；停止末尾选项时 Yarn 层记录了取消异常堆栈，发生在采样结束之后，运行时仍完成清理、退出 0。本轮没有处理这两条错误，不宣称真实运行日志完全无错误。

## Appearance 修复实施与复测

### 实现

修复范围为 layered actor 的 appearance 准备，沿用 `IPreparedActorAppearance` 和现有 Direction appearance slot：

- 当内置准备服务、内置默认 dissolve、无活动 overlay、当前实际图层与源一致、源/目标解析后图层一致时，返回只保留外观身份与提交/结束生命周期的准备对象。它不创建副本、捕获视口或 overlay。原 slot 的时长、等待、替代、Finish、取消和回滚继续生效；结束时仍通过正常 setter 完成外观发布。
- Fade、自定义 dissolve shader、自定义准备服务，以及已有活动 overlay 的情况继续准备完整视觉转场。不能仅按字符串相同省掉任意效果。
- 新副本按原有渲染顺序复制选中的 Sprite，保留纹理、变换、颜色、材质、可见性层和 CanvasGroup 相关属性；分别为源、目标重新应用 masking。未选中的 stencil writer 原本也不参与遮罩，因此不额外复制。仍使用完整 actor bounds 与原捕获池，不改变采样矩形和资源所有权。
- 源头仍会扫描已有 Sprite 来保留顺序，但不再复制之后又隐藏大量无关节点。没有缓存组合图片、共享可变捕获输入或停止实时转场。

### 回归验证

新增/扩展的 layered 回归验证了：

- 等价别名没有创建 overlay，保持稳定角色可见；预先取消、放弃准备、重复 Finish 均正常。
- 等价 appearance 仍按作者给定时长等待；替换未结束 appearance、强制 Finish、事务提交后回滚、随后真实换装均正常。
- 相同 appearance 的 Fade 和自定义 dissolve shader 仍创建视觉输入。
- 合成角色副本恰好包含选中的层，且顺序一致。
- 真实 Metal 渲染将原来的完整副本作为 oracle：合成角色，以及梅露露两套 appearance、艾玛一套 appearance 的源/目标输入逐像素完全一致；真实角色测试包括非单位 opacity，复用现有捕获池。
- 遮罩与捕获池复用测试通过，包括 stencil 覆盖顺序、隐藏 writer、旋转、alpha cutoff、Multiply 和并发租约。
- `tools/test.sh --fast`：582 项单元测试及 Godot headless 集成、失败退出码检查通过，零构建警告/错误。

真实像素测试入口：`--majo-layered-appearance`、`--majo-layered-appearance-real`、`--majo-layered-masks`。GPU 日志归档在修复后 trial00 目录。

**快速推进更容易超出 120 FPS 帧预算，表现为长帧更密集，未出现越来越严重的停顿。** 相同内容约压缩到 27% 的时间，长帧比例约为普通模式的 3.2 倍；最差单帧并未恶化。此结果支持“短时工作密度提高”，不能据此宣称具体 CPU/GPU 单点已被定位。
