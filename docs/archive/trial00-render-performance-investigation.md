# trial00 渲染性能回退调查

日期：2026-09-13。调查版本：`0b44874`（`refactor background actor`），代码对照父版本 `5e2f51a`。

## 结论

已通过当前版本内的交替消融实验，确认背景全景离屏表面的持续重绘是 trial00 的主要性能回退来源之一。停止这一张表面的更新，保留它的纹理供后续镜头采样，固定构图的输出 PNG 字节完全一致，帧率从约 96–102 FPS 上升到 116–119 FPS；重新开启更新后下降。

这足以解释用户观察到的 10–20 FPS 回退量级，但不是完整剧本平均帧率测试，也没有运行父版本作整机 A/B，因此不能声称所有回退均已归因。

## 实现原因

`ManosabaCourtPreparation` 使用 `HorizontalRepeatTexture2D`，将墙面源纹理重复为 15 × 1024 的逻辑长条，即 15360×1024。它原本避免了真正生成整张全景纹理。

新 `GodotBackgroundRaster` 构造函数按 `content.LocalBounds` 创建物理 `SubViewport`，并设置 `RenderTargetUpdateMode = Always`。因此 trial00 即使背景静止，也每帧绘制 15360×1024 的离屏表面，然后通过 `GodotDirectionBackdropVisual` 的 Sprite 再交给各 View 采样。父版本直接把背景纹理交给 Stage 中的 TextureRect，没有这一张原生尺寸的全景中间表面。

新表面包含 15,728,640 像素，单张 RGBA8 颜色存储约 60 MiB（仅按尺寸估算，不是实测总显存分配），面积为 2560×1440 内部画面的约 4.27 倍。新增 draw call 只有约一个，但其填充、纹理写入和后续采样成本不能用 draw call 数量判断。

设计问题是将逻辑空间大小直接等同于物理栅格大小，并把统一的视觉输入抽象绑定到无条件实时重绘。统一 Actor/转场接口本身不要求这样做。

## 测量方式

- Apple M4，Godot 4.7.2 Mono，Metal 4.0 / Forward+。
- 内部 Stage/View/Screen 表面 2560×1440；主窗口 Viewport 1920×1080。
- 关闭 VSync，取消 FPS 上限，从 `Act01_Chapter01_Trial00` 启动。
- 使用外部播放暂停令牌停在开场对白，启动 8 秒后暂停已有 Tween，消除开场 25 秒镜头移动。
- 每阶段预热 1 秒，采样 4 秒的 ProcessFrame 墙钟间隔。FPS 为 1000 / 平均帧间隔。
- 每阶段记录窗口焦点、draw call 和渲染目标尺寸，并在采样结束后保存 ScreenViewport 截图。截图读取发生在采样之外。
- 最终这轮所有采样帧均保持窗口焦点；五个 current/cached 阶段的 PNG SHA-256 完全一致。

| 顺序 / 模式 | 平均帧耗时 ms | P95 ms | FPS |
|---|---:|---:|---:|
| 当前实现 | 9.886 | 10.659 | 101.16 |
| 关闭全景更新、保留纹理 | 8.635 | 9.647 | 115.81 |
| 恢复当前实现 | 10.429 | 13.535 | 95.89 |
| 再次关闭全景更新 | 8.437 | 9.219 | 118.52 |
| 再次恢复当前实现 | 9.850 | 10.670 | 101.53 |
| 直接采样原始重复纹理 | 8.694 | 9.419 | 115.03 |
| 移除 PremultipliedOutput 材质 | 9.821 | 10.621 | 101.82 |

正常模式约 69 draw calls，关闭全景更新后约 68。交替阶段显示约 1.2–2.0 ms 的帧时间差，仍存在运行波动，不应将单次差值当作精确固定成本。

直接采样和移除材质两个模式的截图与基线不同，仅用于性能定位，不是可提交的视觉等价修复。直接采样也只是当前管线中的旧路径近似，不能标记为父版本性能。

当前设备的 Godot GPU 计时接口全部返回 0，视为不可用，不能据此声称 GPU 没有成本。Process 时间监控值受采样/截图等影响，未用于 CPU/GPU 精确归因。现有证据确认的是这条渲染路径的帧时间成本，尚未通过 Metal GPU profiler 分离填充、带宽或同步等待。

最初未冻结镜头的探索轮存在构图差异；下一轮后半段窗口失焦。二者不纳入上表，原始文件分别保留在 artifacts 子目录 `exploratory` 和 `fixed-camera-first`。

## 其他观察与修复方向

1. `GodotActorAppearanceTransition` 的普通外观转场现在持续更新源/目标捕获表面；父版本在准备后停止更新。这是保持动态模型 dissolve 的必要语义之一，但会增加转场期间的成本。本次静止构图没有覆盖该成本，不能从上述数字推断其影响。
2. 多 View 的 Content/Background/TransitionBackground/Composite/View 表面放大总体渲染成本，但大部分结构已在父版本存在，不能全部归为本次回退。
3. `PremultipliedOutput` 材质并未显示与全景重绘同量级的影响，而且负责透明度正确性，不应直接移除。
4. 现有重复墙面 GPU 测试验证了虚拟纹理绘制，没有约束新的完整 Actor→Raster→View 管线的稳态重绘开销；画面正确和单元测试通过不足以避免这次回退。

建议先显式区分静态/脏更新/实时内容，让静态纹理背景避免每帧重绘；不要按 Court ID 写特例，也不要把动态背景与 Live2D 一律冻结。进一步应让普通纹理/重复纹理拥有直接呈现路径，避免仍占用整张全景中间纹理。任意动态节点内容可以保留实时表面，但需要独立考虑分辨率预算及可见性调度。

修复后的验收应同时覆盖：trial00 同构图性能、移动镜头、重复墙面接缝和采样、动态背景与 Live2D dissolve 持续运动，以及转场中断/恢复和表面释放。当前只增加可复现的诊断入口，没有修改正式渲染策略。

## 修复与验收（2026-09-13）

已实施通用纯纹理直绘路径。`BackgroundActor` 通过 `GodotBackgroundContent.FromTexture` 明确声明不可变纹理内容，Direction 保留资源租约并直接绘制纹理，不创建原生尺寸 SubViewport。普通节点内容继续实时绘制，动态背景与 Live2D 的持续转场语义不变。直绘输入使用原始 alpha；离屏输入继续处理预乘 alpha。渲染目标与颜色缓冲估算同步排除了直绘内容。

静态内容的 Freeze 通过独立租约保留相同纹理，支持原 Actor 关闭后保留及再次保留，不调用 GetImage，因此不会破坏虚拟重复纹理。复杂静态节点的脏更新调度不在这次修复范围，默认仍走实时节点路径。

最终诊断入口会临时重建旧全景表面进行交替对照；正常运行不会创建它。本轮所有采样帧均保持窗口焦点，场景固定，结果如下：

| 模式 | 平均帧耗时 ms | FPS |
|---|---:|---:|
| 重建旧全景路径 | 9.844 | 101.59 |
| 修复后直绘 | 8.766 | 114.08 |
| 重建旧路径（重复） | 9.914 | 100.86 |
| 直绘（重复） | 8.731 | 114.53 |
| 重建旧路径（最终） | 9.788 | 102.17 |

该固定场景中恢复约 12–14 FPS，节省约 1.1 ms/帧，并在正常播放中消除 15360×1024 的背景中间表面。诊断为控制变量，在直绘阶段仍保留但停止更新旧表面，所以表中不是实际内存释放后的全剧本测试。旧路径与直绘路径的采样级数不同，不声称 trial00 两者截图逐像素相同。

验证完成：

- `tools/test.sh --fast`：579 项单元测试、headless 集成测试通过。
- GPU `--majo-live-visual`：动态视觉输入、透明背景、直绘静态与实时背景混合 dissolve、自定义背景切换/中断/恢复及释放检查通过。
- GPU `--majo-repeated-wall`：原有重复纹理绘制测试，以及新增完整 Direction 管线的移动/旋转镜头、静态保留和无全景表面检查通过。
- GPU 背景基线：13 张输出 PNG 与原有基线逐字节一致。
- `tools/quality.sh --check` 通过。

完整管线的重复纹理与展开参考图片比较采用 nearest：展开图片的 linear 过滤会跨相邻面板插值，而原有重复纹理的独立绘制在每块面板边缘截断采样。最初使用 linear 对比导致测试失败；检查截图确认该参考差异后，统一采样条件验证几何与像素结果，未改变生产环境的过滤策略。
