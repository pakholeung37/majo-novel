# 实时视觉过渡设计草案

日期：2026-09-11  
状态：讨论草案，暂不实施。接口名称、打断策略与迁移范围尚未定稿。

## 背景与目标

Live2D Demo 暴露了静态截图过渡的限制：在 camera dissolve 中，旧构图中的角色停止运动，新构图中的角色继续运动。当前已对同一 Stage 的 camera dissolve 加入临时实时镜头，但角色外观、背景和镜头尚未形成统一的动态输入契约。

本草案建议统一视觉输入、渲染依赖与资源生命周期，使静态立绘、动态角色、背景和镜头复用过渡算法，同时保留各自的内容实现。

核心原则：Actor 理解自己的外观并提供内容；渲染服务准备画面；Transition Driver 实现视觉混合；Direction 管理状态、时间与事务。冻结是显式策略，不是所有过渡的默认行为。

本文只记录设计方向，不要求立即修改代码、命令、存档或插件接口，也不承诺旧接口兼容策略。

## 与现有草案的关系

- [Background Actor 扩展重构草案](background-actor-extensibility-plan.md)讨论背景的插件注册、Factory 和 Actor 生命周期。本文讨论过渡输入，两者可以衔接，但不要求绑定实施。背景接入 Actor 后，也不应自行重复实现 dissolve。
- [历史视觉转场统一方案](archive/visual-transition-unification-plan.md)保留 Driver、完整画面混合、预乘 alpha 和事务分工等设计参考。其“源冻结在起始画面”的约定不适合动态内容；本文提出替代方向，尚未正式修改该约定。
- 背景草案明确排除了实时双画面 dissolve，本文没有扩大其已约定范围。

## 当前实现与缺口

| 内容 | 当前路径 | 缺口 |
| --- | --- | --- |
| Direction 背景 | Stage 后端准备旧、新背景；每个 View 提供两路背景 ViewportTexture，交给 Driver | 背景内容仍主要受纹理节点契约约束，动态内容的准备和持有协议不完整 |
| 普通贴图角色 | Actor 创建旧、新 Sprite，复用公共外观过渡服务 | 两路内容渲染完成后关闭 Viewport 更新，适用于静态输入 |
| Manosaba 分层角色 | Actor 创建两套完整图层组合，复用同一服务 | 同样依赖固定画面，不能自动推广到持续动画的内容 |
| Live2D 角色 | 外观准备返回直接切换表情的对象，忽略 Driver 和进度 | 尚未实现 Majo 的双外观 dissolve；Cubism 原生表情混合是另一种机制 |
| 同 Stage 镜头 dissolve | 临时旧镜头和目标镜头共享 Stage World2D，持续渲染 | 已解决当前案例，但资源持有方式尚未抽象为通用契约 |
| 跨 Stage 镜头切换、状态恢复 | 保留原有快照路径 | 需要先明确源世界的生命周期，不能直接套用同 Stage 方案 |

相关入口位于 `addons/majo_runtime/Runtime/Direction/Godot/`、`Actors/Godot/GodotActorAppearanceTransition.cs` 和 `demos/live2d/Actors/Live2DCharacterActor.cs`。

## 职责边界

| 层 | 应负责 | 不应负责 |
| --- | --- | --- |
| 内容提供者：Actor、背景、镜头 | 解释外观或构图，准备候选内容，描述动态能力，应用自身稳定状态 | 通用 dissolve/wipe shader、独立的事务调度 |
| 渲染服务 | 分配或复用离屏目标，布局、裁剪、颜色与 alpha 适配，声明依赖，判断首帧就绪 | 决定故事状态或表情含义 |
| Transition Driver | 根据进度混合输入，实现效果的局部资源与清理 | 加载模型、复制角色、推进动作或决定回滚状态 |
| Direction 执行层 | 冲突处理、easing、进度、提交、结束、取消、回滚及持有期 | 理解某个模型的参数或图层名称 |

统一的是输入协议和生命周期，不要求所有内容通过相同节点树实现。`move` 仍走属性插值；角色进出场的透明度变化与外观替换也应保留不同语义。

## 视觉输入契约方向

建议引入“已准备视觉输入”的概念。以下是职责示意，不是待直接落地的 C# API：

```text
内容提供者.PrepareVisualInput(外观或构图, 更新要求, 取消令牌)
    → 可持有的视觉输入

视觉输入
    输出：纹理、尺寸、局部边界、坐标映射、alpha 与颜色空间约定
    更新：静态 / 持续更新 / 显式冻结
    就绪：首帧和渲染依赖已经满足
    持有：保留内容、模型及渲染资源，直到消费者释放

过渡执行
    持有源输入与目标输入
    → Driver.Prepare(源, 目标, 输出表面)
    → ApplyProgress(0..1)
    → 完成或回滚
    → 先解绑消费者，再释放输入
```

静态图片及无动画的图层组合可只渲染一次。动态内容持续更新；“显式冻结”用于明确需要保留某一帧的场景，不得在不支持动态输入时静默降级。

内容提供者声明能力，Direction 根据操作语义提出要求，渲染服务验证两者是否匹配。纯纹理输入不必额外分配 Viewport；Godot 的渲染依赖应留在适配层，避免领域接口直接暴露 RID。

源与目标必须约定一致的输出范围、锚点、裁剪及采样方式。继续沿用统一的预乘 alpha 混合原则，保证端点正确，避免重复应用角色整体透明度或绘制原始内容。

## Live2D 的两种外观变化

### 原生参数混合

困倦到惊讶等表情变化，优先评估 Cubism 原生表情混合：同一模型继续动作、呼吸和物理，只改变表情参数。这是 Actor 的内容行为，不等于画面 dissolve。

需要明确表情对相同参数的覆盖顺序、淡入淡出时间及被下一次表情打断的规则。如何在命令中表达原生混合，与现有 `via` 语义如何区分，留待定稿。

### 显式画面 dissolve

明确要求 `via:dissolve` 时，必须同时提供两种外观的实时画面。两个镜头观察同一个角色，只能得到同一种表情的不同构图，不能替代双外观输入。

理想路径是共享动作时间和基础参数求值，再分别应用源、目标表情并渲染。必须先验证 gd_cubism 是否支持该能力；不能把它当成已存在的接口。

若需要两个模型实例，必须定义动作时间、随机行为、眨眼、物理和事件的同步方式。避免重复发出动作完成事件或其他业务事件；一次业务动画更新与两次视觉渲染应当分开。CPU、GPU 与内存成本需要实测，再决定是否提供此能力。

## 背景与镜头

- 背景切换提供旧、新背景内容的输出；动态背景必须持有各自实例，不能仅保留资源路径。
- 同 Stage 镜头切换共享一个世界，保留旧构图和目标构图，角色模拟只更新一次。
- 跨 Stage 过渡需要持有源 Stage，明确它在过渡期间是否继续模拟，以及何时销毁。作为后续独立范围。
- 状态恢复需要展示一致的恢复边界。保留恢复前冻结画面可以是合理的显式语义，不应机械替换成实时源。
- 镜头 idle、shake 等修饰器在旧、新构图之间如何分配尚待决定；保持构图与冻结整个画面是两个不同概念。

## 渲染依赖与资源所有权

渲染顺序必须覆盖实际消费者，例如 Live2D 蒙版 → 角色输入 → 过渡合成 → 镜头输出 → Screen。共享 World2D 不会自动表达所有离屏输入之间的依赖。

源、目标都完成首帧后才能显示过渡输出。输入不得包含自身合成结果，禁止形成采样反馈环。相同内容供多个镜头使用时，要避免重复模拟，并保留正确的每镜头投影。

渲染服务拥有临时 Viewport、纹理租约和输出节点；内容提供者拥有模型或内容实例；Direction 持有一次操作所需的资源租约。共享缓存不拥有可变角色实例。动态输入的提供者不能在租约释放前销毁内容。

正常结束、快进、取消、回滚、被替换、准备失败、Stage 销毁和运行时关闭都必须释放临时资源。临时镜头不进入公开 View ID、稳定状态或存档；资源统计必须包含它们。

## 打断与恢复策略

草案建议初期保持“完成当前视觉过渡，再开始下一次”的简单规则，与现有实现衔接；代价是打断时可能出现视觉跳变，不能称为无缝接续。

若后续要求无跳变，可显式持有当前混合输出，作为下一次过渡的实时源。这会形成合成链，需要限制深度、并发数量和资源预算，并定义超限行为。不得通过暗中截图冻结来宣称支持实时无缝接续。

回滚恢复稳定内容与呈现绑定；是否精确恢复插件内部动画时间和物理状态是另一项能力，本文不默认承诺。存档默认保存稳定外观及已有的领域状态，不序列化 Viewport 或临时过渡图。

## 建议实施顺序

1. 定稿视觉输入能力、首帧就绪、资源持有与错误处理契约，确认与现有 Actor 接口的迁移方式。
2. 迁移静态角色过渡，保持现有效果；把停止更新从通用硬编码改为输入策略。
3. 将同 Stage 实时镜头源纳入公共渲染资源管理，保留已有的蒙版依赖修复。
4. 增加通用动态内容测试，再接入动态角色或背景适配器。
5. 单独验证 Live2D 原生表情混合与双外观渲染能力，决定支持范围。
6. 根据实际需求处理跨 Stage、复杂打断和背景 Actor 草案的衔接。

以上仅为未来拆分建议，本轮不执行。

## 验证标准与待决问题

未来验收至少覆盖：静态端点一致、动态双输入同帧更新、蒙版无旧帧、多镜头构图正确、角色整体透明度不重复应用、窗口尺寸变化，以及各退出路径的资源回收。测试应读取真实 GPU 输出；headless 只能验证状态与生命周期。

并发场景需要额外覆盖背景过渡与镜头过渡重叠、连续表情切换、Stage 销毁和恢复打断。性能测量应比较模型求值次数、绘制次数、临时渲染目标像素数、显存与帧耗时，不只观察 FPS。

待决问题：

- Actor 现有准备接口如何演进，是否允许破坏性变更？
- 原生表情混合如何对外命名，如何避免与 `dissolve` 混淆？
- gd_cubism 能否共享动画求值并输出双外观？双实例方案能同步到什么程度？
- 动态输入的预算、池化、分辨率策略及能力不支持时的错误如何表达？
- 旧镜头的 idle、shake 与并行背景过渡采用什么语义？
- 是否需要无跳变打断；若需要，允许多深的实时合成链？

这些问题需在实施前进一步确认，本草案不将建议视为已批准的实现要求。
